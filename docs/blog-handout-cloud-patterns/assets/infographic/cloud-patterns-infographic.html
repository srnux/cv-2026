20 CLOUD DESIGN PATTERNS

Grouped by the problem they solve
A

Resilience

Survive failures without taking the whole system down.

A1

Retry

Repeat short-lived failures with growing waits between attempts.

A2

Circuit Breaker

Fail fast while a dependency is down, test again after a cooldown.

A3

Bulkhead

Isolate resource pools so one failure stays contained.

A4

Health Endpoint Monitoring

Report liveness and readiness so orchestrators can react.

B

Messaging and load

Absorb volume and spread work across workers.

B1

Queue-Based Load Leveling

Buffer traffic spikes so the backend works at its own pace.

B2

Competing Consumers

Many workers share one queue, each message handled once.

B3

Publisher-Subscriber

Every subscriber gets its own copy of each event.

C

Data

Scale storage and keep reads fast and consistent.

C1

Cache-Aside

Check the cache first, load from the database on a miss.

C2

CQRSCommand Query Responsibility Segregation

Separate models for writes and reads.

C3

Event Sourcing

Store every change as an immutable, append-only event.

C4

Sharding

Split data across partitions by a shard key.

D

Distributed transactions

Stay consistent when one action spans many services.

D1

Saga

A chain of local transactions instead of one global transaction. Steps before the pivot can be undone, steps after it are retried until they finish.

D2

Compensating Transaction

Undo completed steps with business actions when a later step fails. Refund the payment, release the reservation.

E

Gateway and edge

Control how clients reach your services.

E1

Backends for Frontends

One tailored backend per client type.

E2

Gateway Routing

One entry point sends each request to the right service.

E3

Gateway Aggregation

Merge several service calls into one response.

E4

Gateway Offloading

Move authentication, certificates and rate limits to the gateway.

F

Operations and evolution

Run services well and modernise them safely.

F1

Sidecar

A helper process beside the service handles cross-cutting work.

F2

Strangler Fig

Replace legacy features one route at a time.

F3

External Configuration Store

Settings live outside the deployed code and change at runtime.

Typical combinations A Retry + Circuit Breaker + Bulkhead B → C Events flow into read models C → D Sharding makes Saga necessary E → F Gateway Routing powers Strangler Fig
